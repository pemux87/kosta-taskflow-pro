## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)         (목적)         (구조)        (화면)        (계획)         (규칙)
```

새로운 작업을 시작하기 전 위 순서대로 전부 읽는다.
앞 문서를 읽지 않으면 뒤 문서의 결정 맥락을 이해할 수 없다.

---

## 왜 이렇게 나누는가 — 관심사 분리 원칙

하나의 문서에 모든 내용을 담으면 수정 범위가 뒤섞이고,
어디를 고쳐야 할지 알 수 없게 된다.
각 파일은 **단 하나의 질문에만 답한다.**

| 질문 | 담당 파일 |
|---|---|
| "이 프로젝트가 무엇인가?" | `01-product.md` |
| "어떻게 만드는가?" | `02-specs.md` |
| "화면은 어떻게 생겼는가?" | `03-design.md` |
| "무엇을 언제 만드는가?" | `04-tasks.md` |
| "어떻게 작성하는가?" | `05-conventions.md` |

이렇게 나누면 세 가지 이점이 생긴다.

1. **변경 범위 최소화** — 기술 스택이 바뀌어도 `02-specs.md`만 수정하면 된다.
2. **탐색 비용 감소** — 필요한 정보가 어디 있는지 예측 가능하다.
3. **역할 분담 명확화** — 기획·설계·개발·운영 각 단계에서 참조할 문서가 다르다.
